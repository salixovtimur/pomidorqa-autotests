# Правила набора автотестов PomidorQA

Проект тестирует чужой живой сайт `aiqa.su/pomidorqa` как чёрный ящик. Исходников продукта здесь
нет, стенд общий с другими людьми, база не под контролем. Отсюда все правила ниже.

## Структура

| Где | Что лежит | Чего быть не должно |
|---|---|---|
| `tests/e2e/*.spec.ts` | сценарий и проверки | локаторов, прямых обращений к API |
| `tests/pages/*.ts` | локаторы и действия одного экрана | `expect` — Page Object ничего не утверждает |
| `tests/helpers/*.ts` | тестовые данные, подготовка через API, уборка | проверок и знания об экранах |
| `tests/api`, `tests/unit` | правила и чистые функции | обращений к браузеру |

## Обязательное

**Подготовка через API.** Если тест не проверяет саму форму регистрации, участник заводится
запросом `POST /api/pomidorqa/test/accounts` через `UserPool.add`. Прогон формы ради предусловия —
лишние секунды и лишний повод для флака.

**Уборка за каждым тестом.** Все созданные участники удаляются в `afterEach` через
`UserPool.cleanup`. Контекст попадает в список на уборку **до** первого действия, которое может
упасть: иначе упавшая подготовка оставит аккаунт на общем стенде навсегда. `DELETE` не принимает
идентификатор — он удаляет владельца пришедшей куки, поэтому правило «один браузерный контекст —
один участник» нарушать нельзя.

**Уникальные данные.** Имена, почты и навыки собираются через `uniqueTag`: у тега есть случайный
хвост, а не только метка времени. Два воркера, стартовавшие в одну миллисекунду, иначе получат
одинаковый навык и найдут в каталоге чужого участника.

**Шаги.** Каждое действие и каждая проверка — в своём `test.step` с осмысленным названием на
русском. В шаге-действии только действия, в шаге-проверке только `expect`.

## Проверки

**Отрицание само по себе ничего не доказывает.** `toHaveCount(0)` и `toBeHidden()` проходят
мгновенно на ещё не отрисованной странице. Перед отрицательной проверкой должна идти
положительная: сначала дождаться признака, что страница перерисовалась, потом утверждать, что
чего-то нет.

**`isVisible()` не ждёт.** Это мгновенный снимок. В проверках использовать `expect(...)`,
`isVisible()` допустим только внутри цикла с дедлайном в Page Object.

**Ожидаемые тексты пришпиливаются дословно.** Сравнение двух строк между собой проходит и на
сломанном продукте, который всем отвечает одинаково.

**Дефект не маскируется.** Если продукт расходится с `requirements.md`, тест пишется **по
требованию** и помечается `test.fail()`, а расхождение описывается в `docs/coverage-matrix.md`.
Переписать тест под фактическое поведение и сделать его зелёным — запрещено: такой тест опаснее
отсутствующего.

## Комментарии

Комментариев в коде нет. Имена тестов, шагов и методов должны объяснять происходящее сами.
Если без комментария непонятно — переименовать, а не пояснять.

## Что должен ловить ревью

- локатор в спеке вместо Page Object;
- `expect` внутри Page Object;
- регистрация через форму там, где тест проверяет не форму;
- созданный участник без уборки или контекст, добавленный в пул после падающего действия;
- отрицательная проверка без предшествующей положительной;
- жёсткие паузы `waitForTimeout` вместо ожидания условия;
- тест, подогнанный под фактическое поведение в обход требования;
- новый сценарий, не отражённый в матрице покрытия.
